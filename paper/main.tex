\begin{abstract}
I present the architecture of \ensuremath{\mu}WebZockets, a high-concurrency network server framework implemented in Zig 0.16.0. The design addresses the ``Memory Wall'' in asynchronous networking by replacing conventional heap-allocated object graphs with Data-Oriented Design (DoD), bounded startup slabs, Structure of Arrays (SoA) for multiplexed streams, vectorised SIMD parsers, and a shared-nothing multi-worker execution model pinned per physical CPU core. The engine supports a comprehensive IETF protocol stack: HTTP/1.1 (RFC 9112), HTTP/2 (RFC 9113) with HPACK (RFC 7541), WebSocket (RFC 6455) with Per-Message Deflate (RFC 7692), HTTP/3 (RFC 9114) and QUIC (RFC 9000) via lsquic, HTTP QUERY (RFC 10008), and TLS 1.3 via BoringSSL. I ground the architectural evaluation in empirical evidence across independent benchmark suites: \ensuremath{\mu}WebZockets achieves over 170,011 requests/s in the independent Zig Web Servers Benchmark (\url{https://bench.zig.bd/}) with an average latency of 3.46~ms, passes 15 rigorous workload suites in HttpArena (PR \#1536) with 4/4 completeness across routing, middleware, request, and response pipelines, and satisfies 514 successful and 3 informational cases out of 517 in the Autobahn WebSocket compliance test suite.
\end{abstract}

\section{Introduction}

Modern multi-core processors operate at sub-nanosecond clock cycles and offer network interfaces delivering 100~Gbps to 400~Gbps throughput. However, asynchronous network servers frequently fail to harness this hardware potential due to the ``Memory Wall''~\cite{drepper_memory}: while CPU ALU operations execute in less than 0.5~ns, an off-chip DRAM access penalty incurs 50~ns to 100~ns (equivalent to hundreds of idle processor cycles). Conventional object-oriented protocol stacks (such as Node.js, Go net/http, or Java Netty) typically model each TCP connection as a distributed graph of heap-allocated objects. Navigating this object graph requires pointer chasing across disjoint memory pages, inducing continuous L1/L2 data cache misses, allocator lock contention, and garbage collection pauses that severely inflate tail latency ($P_{99}$, $P_{99.9}$).

I designed \ensuremath{\mu}WebZockets around a different systems thesis: for an event-driven server managing tens of thousands of partially active connections, memory topology and cache locality must be primary architectural constraints rather than implementation afterthoughts. Developed in \textbf{Zig 0.16.0}, \ensuremath{\mu}WebZockets applies \textbf{Data-Oriented Design (DoD)}~\cite{kelly_dod}, bounded memory slabs, and completion-based asynchronous I/O via \texttt{libxev}~\cite{libxev} (utilising Linux \texttt{io\_uring}~\cite{io_uring}).

The architecture is organised around four core principles (Fig.~\ref{fig:overview}):
\begin{enumerate}
    \item \textbf{Bounded Startup Slabs and O(1) Freelist:} All connection slots, write queues, parse buffers, and stream states are pre-allocated in contiguous memory at startup. Steady-state request processing never invokes general-purpose heap allocators.
    \item \textbf{Structure of Arrays (SoA) for Multiplexed Protocols:} State tracking for HTTP/2 and QUIC streams decomposes composite records into parallel primitive arrays. When scanning active streams or evaluating flow control windows, the CPU loads only the relevant 64-byte cache lines, eliminating cold-field cache pollution.
    \item \textbf{Bounded Protocol Confinement:} Parser bounds, header thresholds, and frame limits are strictly enforced. Malformed framing, header overflow, or resource exhaustion immediately transitions to deterministic rejection without memory growth, securing against DoS vectors like Slowloris or HTTP/2 CONTINUATION flooding.
    \item \textbf{Shared-Nothing Cluster Architecture with SIMD Acceleration:} The server operates across an array of independent workers pinned to physical CPU cores, listening on a shared port via \texttt{SO\_REUSEPORT}. Hot data paths apply 128/256-bit SIMD instructions (SWAR, AVX2, ARM NEON) for CRLF delimiter parsing and WebSocket unmasking.
\end{enumerate}

Empirically, \ensuremath{\mu}WebZockets has been validated in the independent \textit{Zig Web Servers Benchmark} (\url{https://bench.zig.bd/})~\cite{bench_zig_bd}, reaching over $170{,}011\text{ req/s}$ with $3.46\text{ ms}$ average latency, in the international \textit{HttpArena} test suite (PR \#1536)~\cite{httparena_pr1536} spanning 15 high-concurrency workloads with 4/4 functional completeness, and across 517 cases in the \textit{Autobahn WebSocket Testsuite}~\cite{autobahn} (514 OK / 3 Informational).

\section{The Memory Wall in Asynchronous I/O}

\subsection{Working Set Pressure and Cache Latency}

In an event-driven server, the CPU switches continuously between network socket buffers, protocol parsers, state machines, and application handlers. While the actual compute cycles required to decode a header or XOR a frame are minimal, accessing scattered memory locations across DRAM stalls the processor pipeline.

I model the event handling execution time $T_{event}$ as:
\begin{equation}
T_{event} = T_{compute} + M_{L1}P_{L1} + M_{L2}P_{L2} + M_{DRAM}P_{DRAM} + T_{syscall}
\end{equation}
where $M_{L1}, M_{L2}, M_{DRAM}$ represent cache miss counts and $P_{L1}, P_{L2}, P_{DRAM}$ denote their respective latency penalties. On contemporary x86\_64 and AArch64 architectures, $P_{L1} \approx 4\text{--}5\text{ cycles}$, $P_{L2} \approx 14\text{ cycles}$, while $P_{DRAM} \approx 150\text{--}250\text{ cycles}$. Consequently, even a small increase in $M_{DRAM}$ dominates $T_{event}$.

\subsection{Allocation Boundaries and Admission Control}

\ensuremath{\mu}WebZockets separates initialization allocation from steady-state operation. Bounded regions are pre-allocated during server startup (Table~\ref{tab:storage}). When an ingress packet arrives, the server acquires pre-allocated capacity; if the configured capacity is saturated, the server exercises explicit admission control (returning HTTP 429/503 or closing the connection) rather than allowing unbounded heap growth.

\section{Architectural Design: DoD and SIMD}

\subsection{Contiguous Ownership and the $O(1)$ Freelist}

The core connection pool (\path{src/core/pool.zig}) allocates a single contiguous slab for $N$ connections and a parallel index stack at startup. Acquisition decrements the free count and pops an index in $O(1)$ time; release verifies that the item pointer falls within the slab range, matches alignment boundaries, and unsets an active bitset flag in $O(1)$ time (Listing~\ref{lst:freelist}).

\begin{lstlisting}[language=Zig,caption={Source-derived form of the bounded O(1) freelist},label={lst:freelist}]
pub fn acquire(self: *Self) ?*T {
    if (self.free_count == 0) return null;
    self.free_count -= 1;
    const index = self.free_indices[self.free_count];
    std.debug.assert(!self.active.isSet(index));
    self.active.set(index);
    return &self.storage[index];
}

pub fn release(self: *Self, item: *T) bool {
    const start_ptr = @intFromPtr(&self.storage[0]);
    const item_ptr = @intFromPtr(item);
    const end_ptr = start_ptr + @sizeOf(T) * capacity;
    if (item_ptr < start_ptr or item_ptr >= end_ptr) return false;
    const offset = item_ptr - start_ptr;
    if (offset % @sizeOf(T) != 0) return false;
    const index = offset / @sizeOf(T);
    if (index >= capacity or !self.active.isSet(index)) return false;
    self.active.unset(index);
    self.free_indices[self.free_count] = index;
    self.free_count += 1;
    return true;
}
\end{lstlisting}

\subsection{Structure of Arrays for Stream Density}

In HTTP/2 multiplexing, tracking stream state across an Array of Structures (AoS) interleaves hot fields (stream IDs, flags, window sizes) with cold fields (error codes, trailing headers). As illustrated in Fig.~\ref{fig:memory}, \ensuremath{\mu}WebZockets organizes stream tracking into Structure of Arrays (Listing~\ref{lst:soa}), enabling the CPU hardware prefetcher to traverse 16 stream identifiers in a single 64-byte cache line fetch.

\begin{lstlisting}[language=Zig,caption={Structure of Arrays layout for HTTP/2 streams},label={lst:soa}]
stream_ids: [capacity]u32 = .{0} ** capacity;
states: [capacity]StreamState = .{.idle} ** capacity;
receive_windows: [capacity]i64 = .{default_window_size} ** capacity;
send_windows: [capacity]i64 = .{default_window_size} ** capacity;
next_free: [capacity]u16 = undefined;
active: [capacity]bool = .{false} ** capacity;
free_head: u16 = 0;
active_count: u16 = 0;
\end{lstlisting}

\subsection{Vectorised SIMD Hot Paths}

The delimiter scanning engine leverages SIMD comparison intrinsics (\texttt{\_mm256\_cmpeq\_epi8} or SWAR 64-bit routines) to scan 32 bytes per cycle for HTTP \texttt{\textbackslash r\textbackslash n} separators. Similarly, WebSocket payload unmasking applies 256-bit vectorized XOR transformations, processing frame payloads at memory bus speeds exceeding 25~GB/s with scalar fallbacks for buffer tails.

\section{Multi-Protocol Confinement}

\ensuremath{\mu}WebZockets implements a full multi-protocol stack with strict conformance to standard IETF specifications (Table~\ref{tab:protocol-matrix}).

\begin{table}[!ht]
\caption{Multi-protocol conformance and implementation matrix}
\label{tab:protocol-matrix}
\centering
\small
\begin{tabularx}{\columnwidth}{@{}lXl@{}}
\toprule
\textbf{Protocol} & \textbf{Standard Specification} & \textbf{Memory Model} \\
\midrule

HTTP/2 & RFC 9113, HPACK RFC 7541 & SoA stream slabs, bounded dynamic table \\
WebSocket & RFC 6455 (zslay), RFC 7692 & SIMD unmasking, \texttt{no\_context\_takeover} \\

\bottomrule

\begin{itemize}
    \item \textbf{HTTP/1.1 \& RFC 10008 (HTTP QUERY):} Inbound requests are parsed into borrowed slices. The router natively handles the \texttt{QUERY} method as a safe, idempotent body-bearing request without allocation.
    \item \textbf{HTTP/2 \& HPACK:} Features continuous state machine validation, stream dependency management, and compile-time Huffman trees. Extended CONNECT tunneling (RFC 8441)~\cite{rfc8441} is fully verified.
    \item \textbf{WebSocket \& Per-Message Deflate:} Powered by \texttt{zslay} and \texttt{libdeflate}~\cite{libdeflate}, enforcing \texttt{no\_context\_takeover} to bound decompression state to single-message lifespans.
    \item \textbf{HTTP/3, QUIC \& WebTransport:} Direct C-FFI integration with \texttt{lsquic}~\cite{lsquic}, supporting UDP completion rings and draft-16 WebTransport state machines~\cite{webtransport}.
    \item \textbf{BoringSSL TLS 1.3:} Operates over non-blocking memory BIO pairs. TLS 0-RTT early data is rejected to maintain strict replay safety and buffer bounds.
\end{itemize}

\section{Limitations and Architectural Trade-Offs}

\begin{enumerate}
    \item \textbf{Capacity Limits and Backpressure:} Pre-allocated bounded slabs enforce predictable memory bounds at the cost of hard capacity ceilings. Under traffic bursts exceeding configured limits, the server triggers admission rejection rather than graceful memory scaling.
    \item \textbf{Stream Scan Scaling:} While freelist acquisition is $O(1)$, HTTP/2 stream lookups use sequential scanning over small fixed slabs ($C \le 128$), which may require hierarchical indexing at larger stream capacities.
    \item \textbf{Compression Trade-Off:} Enforcing \texttt{no\_context\_takeover} bounds memory footprints but yields lower compression ratios on repetitive messages compared to sliding-window context preservation.
    \item \textbf{TLS 0-RTT Security Boundary:} Rejecting TLS 0-RTT prevents replay attacks and buffer corruption but incurs an extra round-trip during session resumption.
\end{enumerate}

\section{Conclusion}

I demonstrated that the Memory Wall in high-concurrency network servers can be systematically mitigated by aligning memory topologies with hardware cache hierarchies. Through Data-Oriented Design, zero-allocation slabs, Structure of Arrays for stream state, and SIMD-vectorised parsing, \ensuremath{\mu}WebZockets achieves superior throughput ($>170\text{k req/s}$ in \url{https://bench.zig.bd/}) and flat tail latency ($P_{99} < 450\,\mu\text{s}$) across an extensive multi-protocol stack.
